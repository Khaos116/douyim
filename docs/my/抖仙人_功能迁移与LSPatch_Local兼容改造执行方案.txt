抖仙人功能迁移与 LSPatch Local 兼容改造执行方案
================================================

文档用途
--------
本文件不是普通功能说明，而是给 Codex / Muse Code / Claude Code / Gemini CLI 等编程智能体直接读取并执行的“项目迁移任务书”。

目标：
1. Fork「抖仙人」作为唯一主工程。
2. 从其他开源抖音 Xposed/LSPosed 项目中“参考并迁移”所需功能。
3. 不把多个项目的 Hook 框架、配置框架、生命周期框架直接混在一起。
4. 最终保持抖仙人的核心架构，并增加：
   - 播放结束自动切换下一条
   - 广告过滤
   - 直播过滤
   - 图文过滤
   - 关键词过滤
   - 长视频过滤（可选）
   - 当前视频无水印下载
   - MP3/音频下载
   - 精确显示点赞数、评论数、收藏数、分享数
   - 发布时间一直显示
   - 发布地点/IP/POI 信息在数据存在时一直显示
   - 文本颜色可配置
   - 可选的 UI 常显/隐藏控制
5. 以 LSPosed 正常运行作为第一基线，同时尽量兼容 LSPatch Local 本地模式。
6. 所有新功能都必须支持单独关闭，并且 Hook 失败时尽量不影响抖音本体启动与播放。

重要：本方案只用于客户端 UI、播放行为、内容过滤和本地媒体保存等功能，不要修改登录、支付、会员、风控、签名校验、设备认证、安全验证或其他访问控制逻辑。

三、核心架构原则
================

整个项目只有一套主状态管理：

DouyinModule
    ↓
FeedContentTracker
    ↓
当前 Aweme / 当前 Feed 状态
    ↓
PlaybackState
    ↓
PlayerHooks
    ↓
各 Feature

禁止出现：

FreedomPlusCurrentAweme
DouPlusCurrentAweme
DouXianRenCurrentAweme

三套并存。

最终统一成：

FeedContentTracker
    ├── currentAweme
    ├── currentPosition（如果能可靠取得）
    ├── currentFeedView / pager（如果能可靠取得）
    └── 当前视频元数据

然后其他模块只读取统一状态。

五、统一配置层
==============

当前抖仙人的配置方式优先保留。

但为了兼容 LSPatch Local，不允许业务 Hook 直接到处调用某个特定 Preferences API。

先抽象：

interface ConfigProvider {
    boolean isMasterEnabled();
    boolean isAutoNextEnabled();
    boolean isAdFilterEnabled();
    boolean isLiveFilterEnabled();
    boolean isImageFilterEnabled();
    boolean isKeywordFilterEnabled();
    boolean isLongVideoFilterEnabled();
    boolean isExactCountEnabled();
    boolean isPublishTimeEnabled();
    boolean isPublishLocationEnabled();
    boolean isCustomTextColorEnabled();

    int getPrimaryTextColor();
    int getSecondaryTextColor();
    int getCountTextColor();
    int getLocationTextColor();

    long getLongVideoThresholdMs();
}

实现至少准备两层概念：

1. LsposedConfigProvider
   - 当前 LSPosed 正常模式
   - 优先复用现有抖仙人设置同步机制

2. LocalConfigProvider
   - 为 LSPatch Local 准备
   - 具体实现必须以实际运行测试结果决定
   - 不要先假设 Modern API Remote Preferences 一定可用

业务功能只调用：

ConfigProvider config

不直接依赖 Remote Preferences。


六、功能一：播放完成自动下一条
==============================

目标：
当前视频自然播放结束后，自动切换到下一条视频。

配置：
autoNextEnabled

要求：
- 默认关闭或沿用产品决定
- 只处理正常 Feed 视频
- 用户手动暂停不能触发
- 拖动到末尾是否触发，应根据播放器真实 completion 回调区分
- 广告/直播过滤产生的“下一条”不要再次重复触发
- 防止同一视频结束事件多次触发
- 切换后重置 completion 状态

优先调查 PlayerHooks：
1. 当前已经 Hook 哪些 TTVideoEngine / VideoEngineListener 回调
2. 是否已有：
   - onPrepared
   - onPlay
   - onPause
   - onCompletion
   - playback state
3. 如果已有 completion 状态，只增加 AutoNextHook
4. 不要重新 Hook 第二套播放器监听

理想流程：

播放器 completion
    ↓
PlaybackState.markCompleted()
    ↓
AutoNextHook.onCompleted()
    ↓
检查 config.autoNext
    ↓
检查当前内容不是过滤跳过中的临时状态
    ↓
debounce / once-per-aweme
    ↓
FeedNavigator.moveToNext()

必须抽出统一：
FeedNavigator.moveToNext(reason)

reason 示例：
AUTO_PLAY_FINISHED
FILTER_AD
FILTER_LIVE
FILTER_IMAGE
FILTER_KEYWORD
FILTER_LONG_VIDEO

这样所有“下一条”只走一个入口。


七、统一 Next 导航
==================

如果当前抖仙人已经有广告/直播/关键词命中后的下一条逻辑：

不要给 AutoNext 再写一套。

抽取现有逻辑：

FeedNavigator.moveToNext(reason)

内部优先级：

方案 A：
调用抖音内部 Pager / Feed 方法

方案 B：
RecyclerView/ViewPager2/自研 Pager 滚到 position + 1

方案 C：
最后才考虑模拟滑动

原则：
尽量调用内部状态正确的切换方式，不优先使用 Accessibility 或屏幕坐标手势。

需要加：
- 500~1000ms 防重复窗口，具体根据测试调整
- currentAweme identity 防重复
- UI 主线程执行
- 异常捕获


八、功能二：广告过滤
====================

抖仙人已有能力时：
优先保留原实现，不重新移植。

AI 任务：
1. 阅读 FeedContentTracker
2. 找出广告判断条件
3. 找出自动下一条实现
4. 将其接到统一 FeedNavigator
5. 确保广告过滤开关独立
6. 确保关闭总开关时不生效

如果现有识别不足，可参考 FreedomPlus 的 Aweme 广告字段判断。

判断必须基于 Aweme 数据，不要只通过：
- “广告”TextView
- View ID
- 屏幕文字 OCR

UI 只是最后兜底。

十二、功能六：长视频过滤
========================

十三、功能七：无水印视频下载
============================

抖仙人已有 VideoDownloader 时：
它是主实现。

AI 首先做差异分析：
1. 抖仙人 VideoDownloader 已支持什么
2. FreedomPlus 支持什么
3. Dou+ 支持什么
4. 只把缺失能力补入抖仙人

不要为了功能更全直接替换整个 VideoDownloader。

建议支持：
- 当前普通视频 MP4
- 图集（如果以后需要）
- Live Photo（如果数据结构支持）
- MP3
- 下载进度
- 下载错误提示

URL 获取统一：
AwemeAccessor.getPlayableUrls()
AwemeAccessor.getDownloadUrls()

下载器不要自己到处反射 Aweme。


十四、功能八：精确人数显示
==========================

目标：
把抖音 UI 中：

1.2万
3.4万
10万+

尽可能显示为：

12,381
34,052
108,941

需要：
- 点赞
- 评论
- 收藏
- 分享

配置：
exactCountEnabled

不要反向解析“1.2万”。
必须从 Aweme statistics 原始模型读取 long/int。

新增：

StatisticsAccessor

接口概念：

long getDiggCount(Object aweme)
long getCommentCount(Object aweme)
long getCollectCount(Object aweme)
long getShareCount(Object aweme)

UNKNOWN = -1

NumberFormatUtils：
formatExact(12381) -> "12,381"

可增加设置：
- 12381
- 12,381

不要用浮点缩写。


十五、精确人数 Hook 策略
========================

优先顺序：

A. 找到抖音负责统计数字 formatter 的方法
   优点：
   - 改动集中
   - View 版本变化影响较小

但必须确认 formatter 是否只用于首页统计数字。
如果它是全局通用 formatter，不能直接全局修改。

B. 找到 Feed action UI bind 方法
   在 bind 当前 Aweme 时覆盖对应 TextView

C. 最后才根据 View 层级寻找 TextView

禁止：
仅凭 TextView 当前文本为“1.2万”就判断它是点赞数。
这样误伤风险太高。

需要做：
- 先 DexKit / 反射定位
- 保存每个版本 resolver
- Hook 失败时只停用 ExactCountFeature


十六、功能九：发布时间一直显示
============================

配置：
publishTimeEnabled

目标显示示例：

2026-09-23 15:32

或者设置允许：

2026-09-23
09-23 15:32

数据来源：
Aweme 创建时间字段。

新增：
AwemeAccessor.getCreateTimeSeconds/Millis()

必须判断单位：
不要把秒当毫秒。

格式化：
使用设备时区，除非用户设置固定时区。

PublishInfoHook：
只负责把数据转换为文本。

FeedUiHook：
负责 View 的创建/显示。


十七、功能十：发布地点一直显示
==============================

配置：
publishLocationEnabled

必须遵守：

如果 Aweme 没有返回地点，显示：
不显示

不要：
- 根据 IP 自行猜城市
- 根据作者主页所在地冒充视频发布地
- 根据 GPS 猜测
- 根据 CDN 地址猜位置

可调查的数据：
- IP location label
- city
- region
- POI
- location
- address
- Aweme 中当前版本可取得的公开展示字段

统一：

PublishInfo resolvePublishInfo(Object aweme)

PublishInfo:
- createTime
- ipLabel
- poiName
- city
- displayLocation

显示优先级可以为：

POI > 视频明确 location > IP label > city

但必须标注语义，避免把“IP属地”叫做“拍摄地点”。

建议 UI：

发布时间：2026-09-23 15:32
IP属地：四川
地点：春熙路（仅当 POI 确实存在）

如果只有 IP：
只显示“IP属地：四川”。


十八、发布时间/地点 UI 策略
===========================

优先：

1. 找到原生发布时间/地点 View
2. 强制 visible
3. 更新文本

如果目标版本根本没有对应 View：

创建一个非常轻量的 TextView/LinearLayout
挂到稳定的 Feed metadata container 上。

不要直接挂 DecorView。
不要使用固定屏幕坐标。

必须：
- 给新 View 设置自定义 tag
- bind 时先查 tag，避免重复添加
- RecyclerView 复用时刷新数据
- 视频切换时清理旧数据


十九、功能十一：文本颜色修改
============================

需要支持至少：

primaryTextColor
secondaryTextColor
countTextColor
publishTimeColor
locationTextColor

设置页使用 Android Color Int 存储。

禁止让不同 Feature 各自 setTextColor。

二十一、LSPatch Local 兼容目标
==============================

官方 LSPatch 仓库已经归档。
因此：

LSPatch Local = 兼容目标
LSPosed = 开发基线

不要反过来为了 LSPatch 先破坏 LSPosed。

阶段：

阶段 1：
原版抖仙人在 LSPosed 正常运行。

阶段 2：
新功能在 LSPosed 全通过。

阶段 3：
再用 LSPatch Local 打包实际测试。

LSPatch 测试项目：

1. 模块是否加载
2. module entry 是否执行
3. scope 是否正确
4. ClassLoader 是否正确
5. DexKit 是否可用
6. Preferences 是否可读取
7. 抖音进程能否读模块配置
8. 视频播放 Hook 是否执行
9. Feed tracker 是否执行
10. 下载是否有存储权限问题


二十二、LSPatch 配置兼容
========================

如果 Remote Preferences 在 LSPatch Local 下不可用：

不要让 AI 立刻重写整个项目。

按以下顺序解决：

方案 A：
确认 LSPatch 当前实现是否已经能够读取现有 Remote Preferences。

能用：
不改。

方案 B：
引入 ConfigProvider，LSPatch 环境使用 LocalConfigProvider。

方案 C：
如果 Patch 后只能可靠访问抖音进程本地数据：
建立只保存非敏感 Feature 配置的本地配置文件/SharedPreferences。

注意：
模块设置 App 与 patched 抖音是不同 UID 时，普通 SharedPreferences 不能直接跨 UID 读取。

因此不要假设：
“换 SharedPreferences 就好了”。

必须基于实际进程、UID、Context 测试。

严禁：
使用 world-readable 等不安全旧方案。


二十三、Hook Resolver
=====================

抖音升级后最容易坏的是类名和方法名。

所有新增功能尽量经过 resolver：

ExactCountResolver
PublishInfoResolver
FeedUiResolver
PlayerResolver

resolver 输出：
- Class
- Method
- Field

Feature 不自己到处 findClass。

启动流程：

DouyinModule
    ↓
resolve hooks
    ↓
打印 resolver 状态
    ↓
只安装成功解析的 Feature

日志：

[AutoNext] READY
[ExactCount] READY
[PublishInfo] FAILED: statistics field not found
[FeedUi] READY

一个 Feature 失败，其他 Feature 继续。


二十四、版本兼容
================

不要写：

if versionName == "40.5.0"

到处散落。

集中：

DouyinVersionCompat

记录：
- versionName
- versionCode

如果某个版本需要不同 Hook：

resolver.resolveV40()
resolver.resolveLegacy()

尽量基于运行时特征匹配而不是只靠版本号。


二十五、DexKit 使用原则
=======================

如果抖仙人已有 DexKit：
复用现有实例与缓存。

不要每次视频切换重新扫描 Dex。

所有 Dex 搜索：
只在模块初始化/首次解析时运行。

结果缓存。

关键词：
- 字符串特征
- 参数类型
- 返回值类型
- 调用关系
- 已知字段结构

避免：
只靠混淆方法名。


二十六、线程要求
================

UI：
主线程。

下载：
后台线程。

反射：
可初始化缓存。

播放器回调：
不要假设一定在主线程。

自动下一条：
切回 Main Looper。

设置更新：
避免阻塞 Feed bind。


二十七、性能要求
================

Feed 每次 bind 是高频路径。

禁止在 bind：
- 扫 Dex
- 遍历整个 ClassLoader
- 读取大文件
- 执行网络请求
- 大量反射搜索

允许：
- 已缓存 Method.invoke
- 已缓存 Field.get
- 简单字符串格式化
- View 更新


二十八、稳定性要求
==================

所有新增 Feature Hook：

try {
    ...
} catch (Throwable t) {
    LogUtils.e(...)
}

但不要无脑把整个模块包一个巨大 try/catch。

应按 Feature 隔离。

如果 ExactCount 崩：
禁用 ExactCount。

不能导致整个 DouyinModule 安装失败。

开始 LSPatch Local 兼容验证。

不要先修改代码。

先使用当前 APK + 当前 LSPatch Local 测试，并记录：

1. 模块入口是否执行
2. Hook 是否安装
3. ClassLoader
4. currentAweme
5. filter
6. playback
7. auto next
8. preferences
9. exact count
10. publish info
11. download

通过日志找到第一个真正失败点。

只有确认失败原因后才修改。

如果问题来自配置：
先抽象 ConfigProvider。

不要假设普通 SharedPreferences 可以跨 UID。
不要使用不安全的 world-readable preferences。

每次只解决一个 LSPatch 兼容问题。

四十八、最终原则
================

这次项目不要追求“移植最多代码”。

真正目标是：

抖仙人 = 稳定核心
FreedomPlus = 功能参考
Dou+ = 下载/Feed 数据参考

最终产物仍然应该看起来像“增强版抖仙人”，
而不是把三个项目硬拼到一起。

最重要的三个技术目标：

1. currentAweme 只有一个来源。
2. 切换下一条只有一个入口。
3. 抖音版本变化时，只需要优先修 resolver/accessor，而不是重写所有 Feature。
